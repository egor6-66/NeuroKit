Прочитай diff и определи, какое поведение меняется. Для затронутых точек входа проверь обычный и граничный сценарии по коду и тестам. Для каждой найденной ошибки укажи файл, условие возникновения и наблюдаемое последствие.

### Приёмка публичного API

Выбери реальный сценарий и набросай минимальный вызов со стороны потребителя, используя только публичный API. Для длительной операции покажи, как её начать, наблюдать состояние и прогресс, отменить и узнать результат или ошибку, если эти действия предусмотрены сценарием. По коду установи, какой объект представляет операцию и какой модуль предоставляет каждую её часть.

Если вызов проходит через несколько модулей, выясни, за что отвечает каждый. Создание агента и его последующий запуск могут быть самостоятельными операциями. Если же потребителю приходится самому соединять состояние и команды одной установки, найди обоснование такого разделения в контракте и правилах проекта. Когда разделение нарушает правило, сразу укажи конкретные публичные символы, нарушенное правило, вынужденные действия потребителя и модуль, в котором нужна правка. До исправления оставь контракт на доработке.

Например, в описанном API NeuroTools `useLocalModelInstallation(id)` отдавал статус, прогресс и ошибку, а начать и отменить ту же установку можно было только через `useModel(id)`. Потребитель дважды передавал ID и сам связывал команды с состоянием. Даже если обе команды срабатывают, контракт требует правки в NeuroTools: хук установки должен предоставлять и состояние, и обе команды.

Проверь размещение новой логики по действующим правилам проекта. Соседняя кнопка показывает, где страница размещает действие. Принадлежность странице подписки на установку и выбора команды обоснуй отдельно. Общую обёртку оцени по тому, какое согласованное поведение она объединяет для разных сценариев. Если она нужна лишь для сборки разнесённого API поставщика, укажи дефект у поставщика. Если запрошено объяснение, дай его. Расширение работ на рефакторинг согласуй до правки.

### Вывод о готовности

Отдельно укажи, какие команды проверены, чему соответствует публичный контракт и какой пользовательский сценарий пройден от начала до конца. Для каждого вывода приведи основание. Если пользователь сообщил о пропавшей кнопке на конкретной карточке, проверь её на этой карточке в указанном состоянии. Успешные линтер и проверку типов запиши как статические проверки. Если сценарий воспроизвести не удалось, назови непроверенный результат и оставь причину открытой.
